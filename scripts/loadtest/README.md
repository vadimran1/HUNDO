# Нагрузочное тестирование HUNDO

Проверяем, сколько посетителей выдержит сайт и где начинает расти время ответа. Тест бьёт **только по своему сайту** и только по лёгким адресам: лендинг, приложение, статика и чтение конфигурации входа. Платный `/api/chat` намеренно не трогаем.

## 1. Установить k6

- **Windows:** `winget install k6` (или скачать с [k6.io/docs/get-started/installation](https://grafana.com/docs/k6/latest/set-up/install-k6/))
- **macOS:** `brew install k6`
- **Linux:** инструкция по той же ссылке

Проверка: `k6 version`.

## 2. Запустить

Из корня проекта:

```bash
# мягкий прогон по рабочему сайту (пик 20 посетителей, ~3 минуты)
k6 run scripts/loadtest/hundo.js

# сильнее и по своему адресу
k6 run -e BASE=https://www.hundo.online -e PEAK=50 scripts/loadtest/hundo.js

# по локальному серверу (сначала: npm run build && node scripts/serve.mjs)
k6 run -e BASE=http://localhost:3000 -e PEAK=100 scripts/loadtest/hundo.js
```

- `BASE` — адрес сайта (по умолчанию `https://www.hundo.online`).
- `PEAK` — сколько одновременных «посетителей» на пике.

## 3. Как читать результат

В конце k6 печатает сводку. Главное:

| Строка | Что значит | Хорошо |
|---|---|---|
| `http_req_duration ... p(95)=` | 95% ответов быстрее этого времени | < 800 мс |
| `http_req_failed ...` | доля ошибок | < 1% |
| `http_reqs ...` | всего запросов и сколько в секунду (RPS) | чем больше держит без ошибок, тем лучше |
| `✓ / ✗ checks` | сколько проверок «пришёл ответ 200» прошло | все ✓ |

Внизу стоят **пороги** (`thresholds`). Если какой-то не выполнен, k6 завершится с ошибкой и подсветит его красным — это и есть «узкое место».

## 4. Как найти предел

Запускай с растущим `PEAK` (20 → 50 → 100 → 200) и смотри, при каком значении `p(95)` уходит за 800 мс или появляются ошибки. Это и есть запас прочности сайта — хороший график для защиты проекта.

> Vercel на бесплатном тарифе может сам притормозить при всплеске (это защита, а не поломка). Статику он отдаёт из CDN и держит много, а предел обычно упирается в серверные функции `/api/*`.
